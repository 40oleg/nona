# RegExp: этап 0.9

Срез: 27 сентября 2026 года. Работа идёт в общей ветке `work/v0.6-v0.14`; PR будет один после завершения всего диапазона.

Литералы RegExp проходят через lexer, AST, binder и IR. Конструктор создаёт native объект с исходным шаблоном, флагами `gimsuy` и собственным `lastIndex`; внутренние строки отслеживает GC. Реализованы проверки флагов и структуры шаблона, копирование RegExp, `Symbol.match`-подобные аргументы, геттеры `source`/`flags` и отдельных флагов, `toString()`, `test()`, `exec()`, а также `RegExp[Symbol.species]`. Parser VM вызывается при создании RegExp и сразу отклоняет неверные квантификаторы, синтаксис групп, недопустимые identity escapes при `u` и ссылки на отсутствующие захваты. Без `u` числовые escapes различают существующие захваты, legacy-octal и буквальные `8`/`9`; такие шаблоны исполняет VM. `test()` вызывает переопределённое свойство `exec`.

Быстрый native matcher обрабатывает простые литералы, точку, классы, сокращённые классы, якоря, границы слова, некоторые повторы и литеральные альтернативы. Для шаблонов с группами, общими альтернативами и повторами `exec()` вызывает VM, написанный на поднаборе JavaScript и скомпилированный самим Nona в отдельном IR. VM разбирает символьные классы один раз при создании RegExp, проверяет диапазоны и использует те же разобранные элементы при сопоставлении; поддержаны литералы, сокращённые классы, Unicode properties, `\x`, `\u` и Unicode code points. Классы с escape-последовательностями исполняет VM. VM разбирает последовательности, группы (включая именованные), альтернативы, классы, жадные и ленивые квантификаторы `*`, `+`, `?`, `{m,n}`, обратные ссылки и базовые lookahead/lookbehind. Захваты обновляются при откате и сбрасываются на новой итерации повторения. Результат `exec()` содержит захваты, `index`, `input` и `groups`, причём именованные `groups` имеют null-прототип. Ядро VM создаётся при первой проверке шаблона и затем используется при сложных вызовах `exec()`.

Поддержка `u` остаётся частичной: native точка захватывает суррогатную пару и `lastIndex` считает UTF-16 единицы; поиск не начинает совпадение со второй половины пары, поддерживается отдельный escape `\uNNNN`. VM обрабатывает суррогатные пары как одну кодовую точку для точки, простых классов и литералов, поддерживает `\u{...}`. Добавлены `\p{…}`/`\P{…}` с данными Unicode 17 для общих категорий, Script, Script_Extensions и двоичных свойств ES2020, в том числе внутри классов. Таблицы генерирует `scripts/generate-regexp-unicode.py` из официального UCD. Исчерпывающая проверка всех комбинаций Unicode folding, классов и lookbehind ещё не завершена. Остаётся дополнить parser VM до полной грамматики и валидации шаблона при создании RegExp, все escape-последовательности, точная семантика backtracking и ограничение ресурсов для патологических шаблонов. Часть интеграции с методами String и Symbol hooks уже выполнена в [этапе 0.10](v0.10-regexp-string-status.md).

Проверки: выбранная группа Test262 `built-ins/RegExp/prototype/exec` — **76/79**. Три оставшихся файла проверяют поздние флаги `d`/`v` или разрешение повторных имён групп после ES2020. Группа `RegExp[Symbol.species]` — **4/4**. Локальные проверки RegExp/VM после числовых escapes — **42/42**, включая стрессовую GC для захватов. Полный Windows-прогон после внедрения VM и исправления точки входа: **1795 pass, 0 fail, 1 skip из 1796**; последующее Unicode-изменение проверено локально. Четыре отдельные Linux-проверки RegExp/VM со стрессовой GC и без неё прошли. Эти выборки не доказывают полного покрытия ES2020 RegExp.

Полный каталог Test262 `built-ins/RegExp/lookBehind` сначала дал **13/17**. VM теперь исполняет тело lookbehind справа налево: разворачивает порядок элементов последовательности, читает символы и обратные ссылки назад, сохраняет границы захватов и применяет жадные повторения в направлении сопоставления. Повторный каталог прошёл **17/17**; пять локальных RegExp тестовых файлов — **46/46**; целевой Linux x64 native сценарий с захватами, жадным повторением и альтернативой завершился успешно. Полная грамматика и Unicode case folding по-прежнему открыты.

Каталог Test262 `built-ins/RegExp/named-groups` сначала дал **20/36**. Общий разбор имён теперь декодирует `\uNNNN` и `\u{…}`, объединяет суррогатные пары и проверяет первый и последующие code points по таблицам Unicode `ID_Start`/`ID_Continue` с разрешёнными дополнительными символами IdentifierName. Повторный каталог — **26/36**: все оставшиеся десять отказов используют повторяющиеся имена групп, разрешённые после ES2020. Локальный регрессионный тест и целевой Linux x64 native сценарий прошли. Каталоги `CharacterClassEscapes` и `RegExp.escape` в закреплённом Test262 целиком используют возможности после ES2020 (флаг `v` и новый метод соответственно); их результаты не оценивают этот этап.

Для `/iu` в таблицы RegExp добавлены простые/common mapping записи `C` и `S` из Unicode `CaseFolding.txt`; для legacy `/i` используется односимвольное верхнее преобразование с запретом перехода не-ASCII символа в ASCII. Шаблоны с `i` исполняет VM, чтобы литералы, классы, `\w` и Unicode property escapes использовали общую канонизацию. Test262 `unicode_full_case_folding.js` вырос с **0/1 до 1/1**; повторный каталог `RegExp.prototype.exec` остался **76/79** с теми же тремя отказами на возможности после ES2020. Локальные проверки `/iu` против `/i`, property escapes, ASCII и GC прошли **3/3**; целевой Linux x64 native сценарий прошёл. Полное покрытие RegExp ES2020 этими выборками ещё не доказано.

Все шаблоны `/u` теперь исполняет VM. В классах исправлено декодирование сырой суррогатной пары и объединение соседних `\u` escapes в одну кодовую точку; `\u{...}` принимает любое число ведущих нулей при значении не выше U+10FFFF. Каталог Test262 `language/literals/regexp` вырос с **210/240** до **217/240**: все семь прежних отказов на Unicode литералах прошли. Остальные 23 файла используют исключённый динамический `eval`. Повторный каталог `RegExp.prototype.exec` остался **76/79** с тремя отказами на возможностях после ES2020. Целевой Windows тест и Linux x64 native тест прошли.

Lexer теперь проверяет литералы тем же parser VM, что и конструктор RegExp, вместо грамматики установленного Node.js. Для этого компилятор исполняет постоянный исходный текст parser VM в изолированном контексте Node; код проверяемого шаблона не исполняется. При переключении обнаружены и исправлены три ранее нестрогих правила VM: braced quantifier без атома, квантификация lookbehind и lookahead при `/u`, неполный `\k` при наличии именованной группы. После исправлений полный каталог литералов сохранил **217/240** с теми же 23 `eval`-зависимыми отказами, `RegExp.prototype.exec` — **76/79** с прежними тремя отказами после ES2020; четыре локальных целевых теста и Linux x64 native сценарий прошли. Полный аудит грамматики ES2020 и пределы ресурсов по-прежнему открыты.

Простой повтор в VM теперь хранит позиции в Uint32Array для длинных входов вместо создания сотен тысяч свойств обычного массива; повтор Unicode property читает кодовые точки напрямую без рекурсивного вызова matcher на каждом символе. Конструктор буфера позиций сохраняется до пользовательских изменений глобального `Uint32Array`. Сгенерированный Test262 `property-escapes/generated/Alphabetic.js`, прежде не завершавшийся за 180 секунд, прошёл при явно заданном таймауте 180 секунд. Измеренный инструментированный запуск занял около 127 секунд: построение второй большой строки в harness — около 74 секунд, два последних RegExp вызова — около 39 секунд вместе. Стандартный 30-секундный таймаут smoke runner для этого файла недостаточен; runner теперь принимает `TEST262_RUNTIME_TIMEOUT_MS` и записывает его в отчёт. Локальный тест жадного/ленивого и обратного повтора, целевой Linux x64 native тест и повторный каталог `RegExp.prototype.exec` **76/79** прошли без новых отказов. Полный каталог Unicode property escapes и общий performance gate 0.9 остаются открытыми.

Несгенерированные 144 теста каталога Test262 `property-escapes` прошли **144/144**. Два сгенерированных файла для `Script=Greek` и `Script_Extensions=Greek` прошли **2/2** при лимите 180 секунд на файл; вместе они заняли около двух минут. Остальные 439 сгенерированных файлов и общая производительность длинных строк ещё не проверены. Runner теперь допускает `TEST262_EXCLUDE_PATH_FILTER`, чтобы независимо запускать обычную часть каталога и тяжёлые генерированные группы.
