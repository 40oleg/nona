# Nona: AOT-компилятор поднабора ES5 для Windows x64

Дата: 2026-09-20. Статус: реализация v0.1 завершена и проверена на Windows x64.
Итог: 147 тестов прошли, 0 ошибок, 1 пропуск из-за прав на symlink; четыре примера EXE запущены.

## 1. Цель и принятые решения

Пользователь хочет компилировать небольшой JavaScript-скрипт в самостоятельный
исполняемый файл для Windows. Согласованы Windows x64, собственный генератор
машинного кода и PE32+, а также TypeScript для самого компилятора.

Результат: консольный `.exe`, который работает без Node.js, C-компилятора,
LLVM, внешнего ассемблера и поставляемых вместе с программой библиотек.
Зависимости от системных DLL Windows допустимы. Node.js нужен для запуска
компилятора, TypeScript — для его разработки и сборки.

Это ограниченный поднабор ES5, а не реализация всего стандарта. Поддерживаемые
операции сохраняют семантику JavaScript. Неподдерживаемые конструкции отвергаются
с диагностикой, а не получают скрыто изменённое поведение.

Предлагаемая первая поддерживаемая среда запуска: Windows 10/11 x64.
Сборка и проверка первой версии выполняются на Windows x64. Кросс-компиляция
и другие архитектуры не входят в критерии готовности.

## 2. Пользовательский интерфейс

После сборки проекта:

```powershell
node dist/cli.js build examples/factorial.js -o build/factorial.exe --target win32-x64
.\build\factorial.exe
```

`win32-x64` — единственная поддерживаемая и целевая платформа по умолчанию.
Ключ `-o` обязателен. Вход — один файл UTF-8, без модулей и подключения файлов.
CLI поддерживает `--help` и `--version`. Неизвестные опции и цели — ошибки.

Успешная компиляция возвращает код 0, ошибка — 1. Диагностика содержит имя файла,
строку, столбец, код и понятное описание ошибки. При ошибке анализа выходной файл
не создаётся и существующий результат не изменяется. Успешная сборка заменяет
указанный результат через временный файл в той же директории; входной файл
нельзя использовать как выходной. Отсутствующие выходные директории создаются.

## 3. Точные границы языка v0.1

### Лексика и выражения

- ASCII-идентификаторы: буквы, цифры после первого символа, `_`, `$`.
- Пробелы, переводы строк, комментарии `//` и `/* ... */`, начальный BOM.
- Десятичные числовые литералы с дробной и экспоненциальной частями,
  шестнадцатеричные литералы. Legacy octal отвергается.
- Строки в одинарных и двойных кавычках с Unicode-содержимым; экранирования
  кавычек, обратной косой черты, `\n`, `\r`, `\t`, `\b`, `\f`, `\v`, `\0`
  без следующей цифры, `\xHH`, `\uHHHH` и продолжение строки через обратную косую.
  Legacy octal escapes отвергаются.
- Значения `true`, `false`, `null`, встроенные имена `undefined`, `NaN`, `Infinity`.
- Скобки, арифметика `+ - * / %`, унарные `+ - !`, `typeof`.
- Сравнения `< <= > >= == != === !==`, логические `&& ||`, условное `?:`.
- Присваивание `=`, `+= -= *= /= %=`, префиксные и постфиксные `++ --`.
  Слева — только изменяемая переменная или параметр.
- Вызовы именованных функций верхнего уровня и встроенного `console.log(...)`.

Побитовые операторы, comma operator, доступ к свойствам и индексам, регулярные
выражения и остальные выражения вне перечисленного поднабора отвергаются.
Запятая разрешена как разделитель деклараций, параметров и аргументов.

### Инструкции и области видимости

- `var` с несколькими деклараторами и необязательными инициализаторами.
- Блоки, пустая инструкция, выражение-инструкция.
- `if/else`, `while`, обычный `for` с необязательными частями заголовка.
- `break` и `continue` без меток, только внутри циклов.
- `function name(parameters) { ... }` только непосредственно на верхнем уровне.
- `return` с выражением или без него, только внутри функции.
- Вставка точки с запятой по правилам ES5 для поддерживаемых конструкций,
  включая перевод строки после `return` и ограничения postfix `++/--`.

`var` имеет область функции; объявления поднимаются и изначально содержат
`undefined`. Инициализаторы исполняются на своём месте. Повторный `var` допустим.
Глобальные переменные доступны функциям. Параметры и локальные `var` затеняют
глобальные переменные. Объявления функций доступны до своего места в исходнике.
Поддерживаются рекурсия и взаимная рекурсия.

Функции не являются значениями в этом поднаборе: нельзя присваивать их переменным,
передавать как аргументы, возвращать, переопределять или объявлять вложенно.
Повторные объявления функций, повторные параметры и совпадение имени функции
с глобальной переменной отвергаются. Локальная переменная может затенить имя
функции, но попытка вызвать такую переменную отвергается.

Недостающие аргументы получают `undefined`; лишние вычисляются слева направо
и игнорируются после вычисления. `arguments` отсутствует. Выход из функции без
`return` возвращает `undefined`. Неявное создание глобальной переменной запрещено.
Чтение необъявленного имени — ошибка анализа, кроме `typeof unknown`, которое
даёт строку `"undefined"`. Имена встроенных значений и `console` зарезервированы
для этого поднабора и не могут переобъявляться.

Объекты, массивы, замыкания, `this`, `new`, прототипы, `eval`, `with`, исключения,
`switch`, `do/while`, `for/in`, метки, директивы strict mode, браузерные API,
Node.js API и синтаксис после ES5 не входят в v0.1.

### Семантика значений

Числа — IEEE 754 binary64, включая `NaN`, бесконечности и отрицательный ноль.
Деление на ноль не вызывает целочисленную аппаратную ошибку. `%` соответствует
остатку JavaScript, включая знаки, дроби и специальные значения.

Преобразования `ToBoolean`, `ToNumber`, `ToString`, сложение и сравнения следуют
ES5 для перечисленных примитивов. В частности, `"2" + 3` даёт `"23"`,
`"2" - 1` даёт `1`, `null == undefined` истинно, `NaN === NaN` ложно.
`&&` и `||` возвращают операнд и вычисляют правую часть только при необходимости.
Порядок вычисления операндов и аргументов — слева направо.

Строки представлены UTF-16 code units с явной длиной; нулевой символ внутри
строки допустим. Сравнение строк — лексикографическое по этим кодовым единицам.
Преобразования чисел и строк не зависят от локали Windows. Корректное округление
при разборе десятичного числа и кратчайшее представление числа при печати —
часть требований, а не замена на фиксированное количество десятичных знаков.

`console.log` принимает любое число примитивных аргументов, преобразует каждый
через `ToString`, разделяет их одним пробелом и завершает строку LF.
Пустой вызов печатает LF; результат вызова — `undefined`. Объект `console`
не материализуется: это распознаваемый компилятором встроенный вызов.
В консоль выводится Unicode через Windows API; при перенаправлении — UTF-8
без BOM. Одиночные суррогаты при кодировании в UTF-8 заменяются на U+FFFD.

## 4. Архитектура компилятора

Поток данных: исходник → токены → AST → связанное представление → IR → x64 → PE.

| Модуль | Ответственность и результат |
| --- | --- |
| CLI | Аргументы, чтение исходника, вызов pipeline, запись результата |
| Lexer | Токены с диапазонами исходника и информацией о переводах строк |
| Parser | AST, приоритеты операторов, вставка точек с запятой |
| Binder/validator | Области видимости, hoisting, разрешение имён, ограничения поднабора |
| IR/lowering | Функции, базовые блоки, значения, переходы и явные операции runtime |
| x64 emitter | Кодирование инструкций, метки, исправление относительных адресов |
| Runtime emitter | Генерация нативных функций для операций над значениями и I/O |
| PE writer | Раскладка секций, заголовки, импорты, relocations, unwind metadata |

IR — внутреннее представление времени компиляции, не байткод для исполнения.
У каждой функции фиксируются локальные слоты, временные значения, размер кадра
и максимальное пространство исходящих аргументов. В первой версии значения
хранятся в стековых слотах; оптимизатор и распределитель регистров не требуются.
Source spans сохраняются до диагностики понижения и генерации кода.

Интерфейс ядра: `compile(source, options)` возвращает буфер PE и метаданные
либо структурированные диагностики. Ядро не читает и не записывает файлы.
Emitter оперирует символическими метками и fixup-записями; PE writer разрешает
межсекционные адреса. Runtime использует тот же emitter, что пользовательский код.

## 5. Представление значений и нативный runtime

`Value` занимает 16 байт: 64-битный тег и 64-битная полезная нагрузка.
Теги различают undefined, null, boolean, number и string. Число хранит сырые
биты double; строка — указатель на дескриптор длины и UTF-16-данных.

Внутренний вызов JS-функции использует Windows x64 ABI с явно переданными
указателем на результат, числом аргументов и указателем на массив `Value`.
Массив создаётся вызывающим кодом; результат копируется в слот вызывающей
функции. Значения возвращаемых строк указывают на память с временем жизни
процесса, а не на стек завершившейся функции.

Строковые литералы находятся в read-only секции. Создаваемые строки и временные
буферы выделяются в собственной арене поверх системной кучи Windows. В v0.1
нет сборщика мусора: арена освобождается при завершении, поэтому бесконечное
создание строк может исчерпать память. Это явно документированное ограничение.
Проверяются переполнения размеров и ошибки выделения памяти.

Собственный runtime реализует преобразования, арифметику и сравнения примитивов,
конкатенацию, форматирование и разбор чисел. Он не использует CRT, JIT или
интерпретатор. Алгоритмы преобразования double требуют отдельных граничных
тестов; обычного `printf("%g")` недостаточно для заявленной семантики.

Внешние вызовы ограничиваются системными функциями выделения памяти,
работы со стандартными потоками, Unicode-конверсии и завершения процесса.
Предполагаемые импорты KERNEL32.dll: `GetProcessHeap`, `HeapAlloc`, `HeapFree`,
`GetStdHandle`, `GetConsoleMode`, `WriteConsoleW`, `WriteFile`,
`WideCharToMultiByte`, `ExitProcess`. Окончательный набор равен реально
используемым функциям и проверяется тестом таблицы импортов.

Штатное завершение программы — код 0. Ошибки памяти и вывода завершают процесс
с кодом 1; диагностическое сообщение в stderr выдаётся, если stderr доступен.
JS-исключения и их перехват отсутствуют. Исчерпание стека остаётся системной
ошибкой Windows, без обещания собственного JS stack trace.

## 6. Windows x64 и PE32+

Emitter сохраняет используемые nonvolatile-регистры, обеспечивает выравнивание
стека на 16 байт в телах функций и резервирует 32 байта shadow space для вызовов.
Для больших кадров необходим probing страниц стека; размеры кадров проверяются.
Используются целочисленные инструкции x64 и SSE2 для double.
Источник: [Windows x64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention).

Генерируется консольный PE32+ для AMD64 с собственным entry point:

- `.text`: код программы, стартовая процедура и runtime, read/execute;
- `.rdata`: константы и литералы, read-only;
- `.data`: глобальные `Value` и изменяемое состояние, read/write;
- `.idata`: дескрипторы импортов, имена и IAT;
- `.pdata` и `.xdata`: таблицы функций и unwind-информация;
- `.reloc`: базовые перемещения абсолютных адресов.

Выравнивания: FileAlignment 0x200, SectionAlignment 0x1000. Все RVA, размеры
и адресные fixups проходят проверку диапазона. Внутренние переходы используют
rel32; данные по возможности адресуются RIP-relative. Абсолютные 64-битные
указатели учитываются в relocation entries. Поддерживаются ASLR и NX;
записываемых исполняемых секций нет. Unwind metadata генерируются для каждой
функции, которой они требуются, даже при отсутствии JS-исключений.
Источник: [Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format).

Entry point инициализирует runtime и глобальные слоты значением undefined,
исполняет инструкции верхнего уровня, освобождает арену и вызывает ExitProcess.
Отладочные PDB, подпись, установщик, ресурсы, DLL-экспорт и FFI не входят в v0.1.

## 7. Проверки и критерии приёмки

1. Тесты lexer/parser проверяют приоритеты, комментарии, escapes, ASI,
   некорректный ввод и точность source spans.
2. Тесты binding проверяют hoisting, затенение, рекурсию и отклонение всех
   явно исключённых конструкций, включая синтаксис ES6.
3. Тесты emitter проверяют байты используемых инструкций, отрицательные
   смещения, переходы вперёд/назад и выход fixups за диапазон.
4. Независимый разбор сформированного PE проверяет заголовки, границы секций,
   imports, relocation entries и unwind metadata; не ограничивается проверкой
   собственным writer того, что он только что записал.
5. End-to-end тесты компилируют и запускают `.exe` на Windows с тайм-аутом,
   сравнивают stdout и код завершения с Node.js для общего поднабора.
   Node.js служит практическим oracle, а ожидаемые значения спорных граничных
   случаев задаются отдельно по ES5. Вывод сравнивается после нормализации CRLF.
6. Матрица включает факториал, Fibonacci, взаимную рекурсию, больше четырёх
   аргументов, пропущенные и лишние аргументы, глобальные изменения, циклы,
   continue в for с выполнением update, short-circuit с побочными эффектами,
   динамическую смену типов, Unicode и встроенный нулевой символ.
7. Отдельно проверяются NaN, infinities, signed zero, дробный остаток,
   поднормальные double, граничные округления decimal/binary64, форматирование
   очень больших и малых чисел, пробелы и некорректные строки в ToNumber.
8. Проверяется перенаправление stdout в файл и pipe, а также запуск результата
   с PATH без Node.js и без проектных файлов. Таблица импортов должна содержать
   только разрешённые системные DLL.
9. В README перечисляются синтаксис, ограничения, команды сборки и запуска;
   примеры содержат арифметику, строки, функции и циклы.

Работа считается завершённой после выполнения этих проверок с реально
запущенными Windows-executable. Одна генерация файла с расширением `.exe`
или успешная сборка TypeScript не подтверждает работоспособность компилятора.

## 8. Порядок реализации и существенные ограничения

Реализация идёт вертикальными шагами: минимальный PE с завершением процесса;
вывод константы; числовые выражения и переменные; переходы и циклы; функции;
динамические примитивы и строки; полная матрица проверок поднабора.
Каждый шаг проверяет исполняемый результат. Промежуточная поддержка части языка
не объявляется завершением всей v0.1.

Наибольшая сложность — точные преобразования строк и double, семантика ES5
и корректные кадры стека/PE metadata. Производительность не является критерием
приёмки первой версии. Расширение языка, оптимизация и сборка мусора — отдельные
последующие задачи; текущая структура допускает их добавление.
